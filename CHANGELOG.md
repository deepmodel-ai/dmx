## [0.8.0] — 2026-10-18

**Upgrading from 0.7.**

1. Run `/dmx/upgrade` once on a branch and commit the refreshed rule files. The rule changed, so loops remind you until you do.
2. The bundled `validate` loop now proposes rework when a required check fails. To keep the old pause, copy `validate.yaml` into `.dmx/loops/` and remove its `rework` block.
3. In a repo with components, run `dmx check`. A Python component whose folder holds no tests now runs the test paths its `paths` map elsewhere, or is reported as not configured. Before, it ran `pytest` in an empty folder and failed.
4. Optional:
   - Add `github_access: gh` under `## GitHub` in `.dmx/config.md` to use the `gh` CLI without a GitHub MCP server.
   - List tests that fail on the base branch too under `known_failures` in a component's `test` entry.

### Added

- **(GH-115)** A loop can fix its own failed checks. With `on_complete.on_failure.rework: {loop: dev, max_rounds: 2, approve: true}`, a run that fails a required check appends a phase to the ticket's `tasks.md`, such as `## Phase 4: Rework — validate, round 1`, with one task per failed check, written from the check's message and findings. It pauses so the developer can edit the tasks; `/loop-continue` then starts the rework loop on that phase (`dev` by default), and when it finishes, the failed loop runs again from its first skill, so `validate` writes a fresh report at the new `HEAD` before it is graded. After `max_rounds` it stops and pauses with every round's findings. `approve: false` starts the rework without the pause, and checking off or deleting the tasks before `/loop-continue` re-runs the loop without a rework run. Failures that aren't code tasks pause as before: a missing test command or toolchain, a component with no `test`, a timeout, a missing or stale validation report, the release checks, a validator error, and any check a validator marks `"reworkable": false`. Optional-check warnings never start rework. Validators can report `"findings": [...]` per check: `run_tests` lists each failed run and the failing-test lines it recognises, and `spec_adherence` lists missing scope items, out-of-scope changes, regressions and unaddressed edge cases. The bundled `validate` loop turns rework on. A new `/rework` command (`rework_loop` tool) runs the same flow on a paused failed run whose loop doesn't set it, or allows more rounds after the limit. While a rework runs, the failed run waits as `reworking`, `loop_status` leads with a line such as "validate — rework round 1 of 2 (dev), then back to validate", and only one run is active at a time. A loop without `rework` behaves as before.
- **(GH-118)** The test gate can accept known failures. A component's `test` entry takes `known_failures: [test id, ...]`, and `.dmx/config.md` takes `test_known_failures:` for `test_command`. A run whose failing-test lines (`FAILED`, `ERROR`, `FAIL`, `--- FAIL:`) all name a listed test passes, marked "known failures only", and the result lists them. A listed test that didn't fail is noted, so the entry can be removed. Any other failure still fails, as does a failed run with no recognisable test lines. `dmx check` lists every known failure, `get_context` includes them, and a failed run's message says where to list one. Before, a test that fails on `main` too, or only on some machines, blocked every change until someone deselected it.
- **(GH-120)** dmx works with the `gh` CLI when no GitHub MCP server is connected. `/dmx/init` tries the server first. Without it, a signed-in `gh` that can see the repo is enough, and init records `github_access: gh` (or `mcp`) in `config.md`. The rule maps each GitHub tool the skills call (branches, PRs, issues, comments) to its `gh` command, and each skill that calls GitHub points to that table. `dmx check` reports which access is set and, for `gh`, whether it's installed and signed in. Before, init stopped without the MCP server even when `gh` was signed in.
- **(GH-119)** `/dmx/init` checks GitHub access before asking anything, and checks the Atlassian server right after the Jira answers. A developer who has to set one up no longer answers every question twice. Its stop messages give the setup for Claude Code, Cursor and VS Code, not only Cursor. When `.gitignore` hides a rule file it wrote, such as `.claude/*`, it offers a negation like `!.claude/rules/` and confirms it with `git check-ignore`, so teammates get the rule. At the end it offers to commit the setup on the base branch or open a setup PR, because loops start from the base branch. `detect_invoking_ide` also recognises Claude Code from the environment it gives its MCP servers. The README's quick start now says dmx needs the GitHub MCP server or a signed-in `gh`.
- **(GH-130)** Fewer avoidable gate failures. When `/dmx/init` or `/dmx/add-component` writes a component's test command, it reads the CI workflow job that runs those tests, copies its environment variables and pytest flags, and says which came from CI. Eval run 2 lost 93 tests to a check CI turns off. When the developer asks for a dmx setup change during a ticket (`.dmx/config.md`, `.dmx/components/*`, `.dmx/loops/*`), the rule says to make it in its own commit and record it in the spec's Scope right away. The validate review then counts a recorded setup change as covered scope, not scope creep, while an unrecorded one still is. In both eval runs, an approved test-command change failed the scope check and cost a full rework cycle.

### Changed

- **(GH-122)** Loop state is committed when a chain stops, not at every step. A loop that chains to the next, or rework returning to the failed loop, no longer makes its own `chore: sync loop state` commit; the next commit (`commit`, `create-pr`) picks the state up. A loop with no next loop, or a chain the branch guard blocks, still commits its final state (GH-23). In the first eval run, these commits were 6 of the branch's 12.

### Fixed

- **(GH-129)** `known_failures` work with pytest-pretty, which replaces pytest's `FAILED` lines with a "Summary of Failures" table (adding `-rfE` doesn't bring them back). When there are no `FAILED` lines and the table is there, `run_tests` reads the failing tests from pytest's own section headers, setup errors included, and takes file paths from untruncated table rows. Rework findings use the same lines. A failed run whose known failures couldn't match, because no failing-test line was recognised, now says so. The hint and `/dmx/init` explain that an entry matches every failing test whose line contains it, so a file, a class or a test name covers what's in it.
- **(GH-121)** Smaller fixes from the first eval run:
  - **PR titles.** `create-pr` follows a PR title convention the repo documents (`CONTRIBUTING.md`, `AGENTS.md`, `CLAUDE.md` or the PR template) instead of dmx's "Feature | …" format, and says so.
  - **Rework tasks.** A check with findings becomes a short task, ``Fix `check` (tool)``, with the findings under it, each up to 300 characters, so the same text no longer appears twice cut off at 200.
  - **Job folder moves.** The reply that moves a pending job folder to its real id says where the files went.
  - **Branch names.** Branch slugs stop at 40 characters at a hyphen.
  - **Commit types.** `commit` picks `docs` for spec, memory or docs-only changes and `chore` for loop state alone, before falling back to the branch prefix.
- **(GH-117)** A Python component whose package folder holds no tests, as in a monorepo that keeps every package's tests in a root `tests/` folder, now runs the test folders and files its `paths` map elsewhere, with pytest from the repo root (for example `uv run pytest -q tests/models tests/test_agent.py`). Before, it ran `pytest` inside the package folder, collected nothing and failed. A component with no tests anywhere has no default command and is reported as not configured. pytest's "no tests ran" (exit 5) is reported as "collected no tests" with the `test: {cmd: ..., cwd: ...}` key to set, and isn't reworked. `get_context` lists each component's test command and whether it comes from `test` or the default, `dmx check` and the "not configured" message show the key's shape, and `/dmx/init` and `/dmx/add-component` explain it.

## [0.7.1] — 2026-10-18

### Fixed

- **(GH-112)** dmx works on Windows, and CI now runs the full suite on Windows as well as macOS and Linux, for Python 3.11–3.13, with every toolchain required. `run_tests` finds commands installed as `.cmd` files, such as `npm`, `pnpm`, and `yarn`, which it reported as "not found on PATH" before, including for the root `npm test` it has used since 0.1. An MCP root such as `file:///C:/Users/me/repo` resolves to that folder; it pointed at the wrong path before, so dmx couldn't find the repo. Shared-source mirror and cache folders get a short name for a long address (a readable tail plus a hash) so they stay under Windows' 260-character path limit; short addresses keep their names. Skill files are read as UTF-8 rather than the locale's code page, test and validator output is decoded as UTF-8 with undecodable bytes replaced, loop-state writes retry briefly when Windows refuses to replace a file another thread is using, and cached trees and git mirrors with read-only files can be deleted. Skill root paths and paths in notes use `/` on every OS. `test:` overrides and `test_command` run through `sh`, so on Windows they need Git for Windows; a missing `sh` says so.

## [0.7.0] — 2026-10-18

**Upgrading from 0.6.** Nothing moves, and components are opt-in: a repo without `.dmx/components/` behaves as in 0.6.

1. Run `/dmx/upgrade` once on a branch and commit the refreshed rule files. The rule changed, so loops remind you until you do.
2. To split a monorepo into components, re-run `/dmx/init` (it finds pnpm, npm, yarn, `go.work`, `uv` and Cargo workspaces) or run `/dmx/add-component <path>` for each service. Then fill in `depends_on`, add `test_command` to `.dmx/config.md`, and add the suggested `CODEOWNERS` lines.
3. Run `dmx check` and fix what it reports. It exits 1 on an error, so it can run in CI too.
4. With components, `run_tests` runs each touched component's tests with its own toolchain. CI that runs the validate loop needs those toolchains (Go, Node with pnpm or yarn, uv, Cargo) installed.

### Added

- **(GH-92)** Tickets can go to more than one Jira project or GitHub repo. `config.md` may list `jira_projects: [LEDG, PAY, BILL]` or `github_issue_repos: [acme/mono, acme/ledger-issues]` (one line, read as YAML; `project_key` and `owner/repo` stay the defaults), and a component may set its own default in `component.yaml`: `ticket: {jira_project: PAY}`, or `ticket: {github_repo: acme/ledger-issues, github_labels: [area/ledger]}`. A new `ticket_destination` tool, which `create-ticket` and `derive-ticket` call, picks what the developer named, else the ticket's components' default, else the repo default, and asks first whenever dmx made the choice, such as "Create the ticket in LEDG (default for ledger)?"; when components disagree it lists each option and asks which. An issue in a repo other than the default is written `acme/ledger-issues#7` in references and closing keywords and `ledger-issues-7` in branch names, job ids and the spec's `ticket`, with `issue_repo` in the spec frontmatter, so no `/` or `#` reaches a path; `create-pr`, `draft-pr-description`, `commit`, `plan` and `close-ticket` use it, and `create-branch` and `/dmx/hotfix` accept a ticket in another repo and keep its reference. Release notes match keys from every allowed project and repo, and `/dmx/status` lists tickets from all of them. `dmx check` warns about a component default outside the allowed list. A repo with one destination, or no ticketing, behaves as before.

- **(GH-91)** `dmx check` on the command line and `/dmx/check` in chat (through a new `check_setup` tool) validate the dmx setup and show what the current branch will load and run. It never changes a file and exits 1 when there is an error. **Setup** reports, each with the command or edit that fixes it: broken `component.yaml` files, `depends_on` ids that aren't components, dependency cycles, two components owning the same pattern, `paths` that match no file (moved?), components with no default test command and no `test`, shared-source locks that don't match their `shared-sources.yaml` (unlocked, locked from another address, or no longer declared), repo-wide and per component, and learnings tagged for a component that doesn't exist, as errors; a missing toolchain for a default command, workspace packages no component covers (`/dmx/add-component <path>`), components without a `CODEOWNERS` line (or no `CODEOWNERS` file), no `test_command` in a repo with components, stray `.dmx/` folders without `config.md`, and custom code that still names the old ticket-file or vendor paths, as warnings; and how many learnings wait for each owner. **This branch** shows the ticket's components with why each is included (spec, changed files, IDE folder, or the component it depends on), the repo-wide files changed, the memory files the agent reads, each standard loop's validators including component ones, and the test commands `run_tests` will run, from the same functions the loops use. A repo without components gets the lock, stray-folder, and old-path checks and its root test command.

- **(GH-90)** A component can declare its own shared sources in `.dmx/components/<id>/shared-sources.yaml`, locked in `.dmx/components/<id>/shared-sources.lock`. `/dmx/update-shared-sources <component>` (the `update_shared_sources` tool's new `component` argument) updates only that lock, so the component's team bumps its sources without platform approval, and its summary marks loops and validators as code to review as before. Its skills, loops and validators resolve after the component's own files, as `<id>/<name>`. Every tree is cached in the repo's `.dmx/.cache/`, so two components on the same source at the same commit share one copy. A component source that isn't locked is skipped rather than vendored, and `dmx fetch-shared-sources` now fetches every lock, repo-wide and per component, naming each component source as `<id>/<name>` and the command that fixes it. To have platform review every component bump instead, add `/.dmx/components/*/shared-sources.lock @<platform-team>` to `CODEOWNERS`; then platform approves skill-only bumps too.

- **(GH-90)** Components can keep their own skills, validators, and loops in `.dmx/components/<id>/skills/`, `validators/`, and `loops/`. Skills and loops are named `<id>/<name>`, such as `ledger/reconcile` or `/dmx/run-loop ledger/backfill`, and only a ticket that includes the component may use them; `get_skill_definition` and `run_loop` refuse others and say to add the component to the spec's `components` list. A plain name never reaches a component folder, so plain names and the standard spec, plan, dev, validate, and release loops resolve as before. A component loop's runs are recorded as `ledger/backfill`, in `ledger--backfill-<task>.json`. `validators` in `component.yaml` adds validators to a named loop for tickets that include the component, after the loop's own: a bare name requires every check it reports (and one that reports none is judged by its own pass), and the loop-YAML shape (`tool`, `checks` with `required`, `timeout_seconds`) gates by its required checks. A component validator is looked up in the component's `validators/` first, then the repo-wide places, so a component can also add a repo-wide or bundled validator. Its check names carry the component (`ledger/reversible`) in results and the pause message, so they never collide with repo-wide checks and name their owner; a broken entry fails instead of disappearing. A ticket for two components runs both components' validators. `list_skills` lists the ticket's component skills first, as `ledger/reconcile (ledger)`, and `get_context` lists component skills and validators with their paths.

- **(GH-88)** In a repo with components, memory is scoped to the ticket's components. `get_context` lists the repo-wide memory, the memory of each of the ticket's components, and the memory of the components they directly depend on (one level), so a payments ticket reads ledger's notes and a ledger ticket doesn't read payments'. Writing follows ownership: `get_context`'s new `editable_memory` is the components whose files the branch changed, plus `repo-wide` only when it also changes the repo-wide dmx setup (`config.md`, `.dmx/loops/`, `.dmx/skills/`, `validators/`, the shared-source files); a memory edit alone never qualifies, so no ticket PR needs platform approval for a note. `commit`, `create-pr` and `update-memory` tag each open learning or decision with its owner (`- [ledger] …` or `- [repo-wide] …`; untagged items count as repo-wide), write those whose owner is editable into that owner's memory (`.dmx/components/<id>/` for a component), and leave the rest tagged, so they merge with the PR and wait. `create-pr` also folds in the learnings waiting in earlier tickets' job folders for its editable owners and marks each one with where it went (`→ ledger, <branch>`) through a new `mark_learnings_folded` tool, and lists where every learning went in its result and the PR description. `/dmx/update-memory <component>` or `/dmx/update-memory repo-wide` folds one owner's waiting learnings on demand (`get_context` takes `waiting_for`). An unmarked item in another ticket's folder is waiting; `get_context` returns `waiting_learnings` for the ticket's components and `repo-wide`, and `waiting_counts` for every owner, which `/dmx/status` shows. `prune-jobs` now keeps a job only while it has an unmarked item, including one tagged for a component that no longer exists. `/dmx/sync-branch` keeps one copy when both sides folded the same learning. A repo without components reads and writes memory as before.

- **(GH-89)** In a repo with components, `run_tests` runs the tests of each component the branch changed, plus every component that depends on one of them through `depends_on`, directly or through others, instead of one root command. A change outside every component runs `test_command` from `config.md` (the whole line, so `make test && make lint` works), or every component's tests when none is set, so a `go.mod` or lock-file bump never runs zero tests; a branch with no changes does the same. Go, Node, Python and Rust components need no `test` entry: `go test ./...` in a folder with its own `go.mod`, else `go test ./<path>/...` from the module above it; `pnpm --filter <name> test`, `npm test -w <name>` or `yarn workspace <name> test` for a workspace package, else `npm test` when the package has a test script; `uv run pytest -q` when a `uv.lock` is in or above the folder, else `pytest -q`; `cargo test -p <crate>` from the Cargo workspace, else `cargo test`. `test` in `component.yaml` replaces the default and runs through `sh -c` from its `cwd`, or the repo root. A touched component with neither is reported as not configured and fails the check. Identical commands run once, all runs share the validator's time budget, and the message has one line per run, such as `✗ payments — go test ./... in services/payments (exit 1)`; the `tests_pass` check carries each failing run's output under its component's name, so the pause message names the component and the test. A missing toolchain reads "`cargo` not found on PATH". A repo without components runs what it runs today.

- **(GH-87)** `/dmx/add-component <path>` makes one folder a component. A new `add_component` tool recognises what the folder holds, in this order: a `go.mod`, a `Cargo.toml` with `[package]`, a `pyproject.toml` with `[project]`, a `package.json`, or Go code under a module above it (a service in a single-module repo, described by its import path). It takes the id and description from that, the same way `/dmx/init` does, or from the `id` and `description` arguments. Go, Node, Python and Rust components get no `test` entry, so the default applies; a folder in any other language is named after itself and its `component.yaml` gets commented `test` lines to fill in, which the skill points out. A taken id, including a folder whose `component.yaml` is broken, is never reused: nothing is written and the reply suggests the folder path as an id, which the skill asks about. The repo root, `.dmx/`, a path outside the repo, a missing folder, and a folder another component already covers exactly are refused; a folder inside another component is allowed and named as carved out of it. The skill shows the plan, asks once, writes the file (never overwriting one), offers to move repo-wide memory about the component into its folder as a diff, and prints the `CODEOWNERS` line. It does not commit.

- **(GH-86)** `/dmx/init` finds components in workspace files: `pnpm-workspace.yaml` (with `!` exclusions), `package.json` `workspaces` (npm, or yarn when there is a `yarn.lock`), `go.work` `use` lines, `[tool.uv.workspace]` and Cargo `[workspace]` `members` and `exclude`. Each member folder with its manifest becomes a proposed component with `paths: ["<folder>/**"]`, an id from the package, module, project, or crate name (any `@scope/` or module path dropped; the folder path when two would clash or the id is taken), and the manifest's description. The root folder is never a component, and a member an existing component already covers is not offered again. `/dmx/init` asks only when there are at least two, so a single-product repo is not asked; it writes the ones the developer keeps through a new `detect_components` tool, which never overwrites an existing `component.yaml`, leaves `depends_on` to the developer, suggests the `CODEOWNERS` lines, and offers to move component-specific parts of the repo-wide memory into each component's folder as a diff to confirm. Re-running `/dmx/init` in an existing monorepo adds its components.

- **(GH-86)** Components: a monorepo can declare each service or package in `.dmx/components/<id>/component.yaml`, with a required `description` and `paths`, and optional `depends_on`, `test`, `validators` and `ticket` that later 0.7 releases use. `paths` are gitignore-style globs from the repo root, and when they nest, such as `services/payments/**` and `services/payments/sdk/**`, the most specific one owns the file; files no component matches are repo-wide. A ticket's components are the `components` list in its `spec.md` frontmatter, which `create-ticket`, `derive-ticket`, `create-branch` and `/dmx/hotfix` write and ask about when unclear, plus every component whose files the branch changed (committed or not, both sides of a rename, never `.dmx/` itself). With no list in the spec, the component holding the folder the IDE opened is used. In a repo with components, the first line of every `run_loop`, `loop_advance`, `loop_continue` and `loop_status` message names them, such as `Components: ledger (.dmx/components/ledger/), payments (.dmx/components/payments/)`, or `Components: none (repo-wide)`; editing the list corrects it on the next message. A new `get_context` tool returns the ticket's components and why each is included, the repo-wide files it changed, the memory files to read (repo-wide, then each component's `*.md`), the ticket's files, and the skills and validators that apply with their paths. The rule calls it before a task when `.dmx/components/` exists, and a broken `component.yaml` is skipped and named once. A repo without `.dmx/components/` behaves as before. The rule changed, so the workflow version is 0.7.0; run `/dmx/upgrade` once after updating.

## [0.6.0] — 2026-10-17

**Upgrading from 0.5.** 0.6 changes the `.dmx/` layout, so each repo migrates once:

1. On a branch, run `/dmx/upgrade`. It refreshes the rule files, shows the migration plan (ticket files moving into job folders, shared sources locked instead of vendored, custom code that still names the old paths), asks once, and applies it. Fix any custom code it lists, then commit everything as one PR.
2. Before merging the upgraded `branch_base` into a branch cut earlier, run `/dmx/sync-branch` or any loop step on that branch, so its own ticket files move into its job folder first. If a merge still stops on a modify/delete conflict in `.dmx/spec.md`, `.dmx/tasks.md`, or `.dmx/activeContext.md`, keep the branch's version; the next loop step moves it.
3. CI that runs shared validators needs read access to the shared-source repos: give it a read token and run `dmx fetch-shared-sources` before the tests.
4. The first PR opened by the release loop after the upgrade may remove many old finished jobs in one commit. To keep them, add your own `.dmx/loops/release.yaml` without the `prune-jobs` step.

`/dmx/sync` still works in 0.6 as an alias for `/dmx/update-shared-sources`.

### Added

- **(GH-84)** The release loop removes finished jobs before it opens the PR. A new `prune-jobs` step runs before `create-pr` and removes each job folder in `.dmx/jobs/` whose loop runs have all finished, that is on `branch_base` (its PR merged), and whose newest run finished more than 30 days ago; a folder with no runs uses the date of its last commit on `branch_base`. It never removes the current ticket, a job with an unfinished or unreadable run, a job whose `activeContext.md` still has Open Learnings or Open Decisions, or a job with uncommitted changes. The removals are their own commit, "chore: remove N finished jobs", which holds nothing else even when other changes are staged, and the drafted PR description gets one line telling reviewers they can skip it. Git history keeps the files. Nothing is removed on `branch_base`, `production_branch`, or a detached HEAD. A repo that wants to keep job history uses its own `.dmx/loops/release.yaml` without the step. `dmx prune-jobs --older-than 7d` runs it by hand, and `--dry-run` shows what would go and why each other job stays.

- **(GH-84)** `/dmx/upgrade` migrates a 0.5 repo's ticket files after refreshing the rules. A new `migrate_dmx_layout` tool plans the change first: this branch's root `spec.md`, `tasks.md`, and `activeContext.md` move into its job folder; root files left by an earlier ticket are deleted (their content stays in git history); custom validators, loops, skills, and vendored shared sources that still name `.dmx/spec.md`, `.dmx/tasks.md`, `.dmx/activeContext.md`, or `.dmx/vendor/` are listed with their line; and `.gitattributes` gains the line that collapses loop state. The skill shows that plan, asks once, promotes any open learnings or decisions from a root `activeContext.md` it is about to delete, then applies it. The tool refuses on `branch_base`, `production_branch`, and a detached HEAD, and does not commit. Leftovers are deleted rather than moved because git treats a move as a rename: a branch still on the 0.5 layout that merged the result would get its own edits applied to the earlier ticket's files, with no conflict. A deletion makes that merge a visible modify/delete conflict, resolved by keeping the branch's version. If a merge or rebase does put this branch's files in another ticket's job folder, `run_loop`, `loop_advance`, and `loop_continue` move them into this ticket's folder, restore the other folder from `branch_base`, and say so. `/dmx/sync-branch` moves a 0.5 branch's ticket files before it merges or rebases, and names the one-step resolution when only ticket files conflict.

### Changed

- **(GH-85)** Shared sources are locked instead of copied. `/dmx/update-shared-sources` (formerly `/dmx/sync`) writes `.dmx/shared-sources.lock` with each source's commit and a `sha256` hash of its tree, and only the lock is committed. The content is fetched into the git-ignored `.dmx/.cache/<repo>@<commit>/` through a bare git mirror per remote in `~/.cache/dmx/git/` (or `$XDG_CACHE_HOME/dmx/git/`), the first time a loop, `list_skills`, or `get_skill_definition` needs it. Two sources naming the same repo at one commit share one tree. By default only sources that are new or whose address changed are looked up again, so a floating `?ref=main` moves only when you name the source or pass `all`. A cached tree is checked against the lock's hash after every fetch and again when its files change; a mismatch is fetched again, and refused if the fresh copy still differs. The update's reply carries a summary for the PR: old and new commit, a GitHub compare link, and the skills, loops, and validators added, removed, or changed, with loops and validators marked as code to review. A failed fetch names the source, the commit, and how to fix access. `dmx fetch-shared-sources` fetches exactly what the lock says without changing it, for CI and fresh clones. `/dmx/sync` stays in 0.6 as an alias. `/dmx/upgrade`'s migration locks each source vendored in `.dmx/vendor/` at the commit its `.lock.json` recorded, by fetching it, then removes `.dmx/vendor/` and git-ignores `.dmx/.cache/`; if a source cannot be fetched, `.dmx/vendor/` stays and still resolves. A source the lock does not cover yet keeps resolving to its vendored copy, and an address edited in `shared-sources.yaml` keeps resolving to its locked commit until the update runs; `dmx fetch-shared-sources` reports that mismatch. **Upgrade note:** CI that runs shared validators now needs read access to the shared-source repos — give it a read token and run `dmx fetch-shared-sources` before the tests.

### Changed — Breaking

- **Memory bank layout (branch-scoped model)** — `spec.md` and `tasks.md` now live directly at `.dmx/spec.md` and `.dmx/tasks.md` on the feature branch instead of the nested `.dmx/tickets/active/{ref}/` path. The `tickets/active/` and `tickets/archived/` directories are no longer created by `/dmx/init` and are not used by any skill. `spec.md` now includes a YAML frontmatter block (`ticket`, `branch`, `summary`, `ticketing`).
- **`activeContext.md` repurposed** — no longer holds an `## Active Ticket` pointer or `## Current Focus`. Now functions as a **learning inbox** with three sections: `## Open Learnings`, `## Open Decisions`, `## Session Notes`. Items are promoted to durable core files on commit and PR; the file is fully refreshed by `/dmx/update-memory`.
- **Workflow version marker updated** — IDE rule files now embed `<!-- deepmodel:dmx:start 0.2.0 -->` (SemVer) instead of the legacy `workflow-v1` string. Re-run `/dmx/init` to refresh existing projects.
- **`ticket_id` argument removed** from `/dmx/plan`, `/dmx/implement-next-phase`, `/dmx/implement-next-task`, `/dmx/validate`, `/dmx/update-memory`, `/dmx/create-pr`, and `/dmx/draft-pr-description`. All skills now derive ticket context from `spec.md` frontmatter or branch-name parsing.
- **`/dmx/close-ticket` is now git-clean** — removed the ticket folder archive step and the `activeContext.md` clear step. The skill performs external-only cleanup: ticket transition, PR comment, and branch deletion. Memory was already synced by `/dmx/create-pr`.
- **Configurable branch roles** — release, hotfix, and ship skills read `branch_base` (integration) and `production_branch` from config instead of assuming `master`.

### Added

- **`production_branch` config field** — set by `/dmx/init` alongside `branch_base` in `.dmx/config.md`. Defines the production/release branch for hotfixes, release merges, tags, and back-merges.
- **`/dmx/create-pr` hotfix base auto-detect** — when `base` is omitted and spec marks `**Type:** hotfix` (or branch prefix is `hotfix-`), PR targets `production_branch` instead of `branch_base`.
- **Three-tier memory sync model**: light sync on `/dmx/commit` (promotes qualifying inbox items, appends to Session Notes), full sync on `/dmx/create-pr` (promotes all remaining inbox items, extracts durable learnings from spec/tasks), deep sync on `/dmx/update-memory` (reconciles contradictions, rebuilds `activeContext.md` structure).
- **`spec.md` YAML frontmatter** — `ticket`, `branch`, `summary`, `ticketing` fields written by `create-ticket`, `derive-ticket`, `hotfix`, and `create-branch`. Consumed by `plan`, `implement-*`, `validate`, `commit`, `create-pr`, `draft-pr-description`, and `close-ticket`.
- **`draft-pr-description`** now reads `spec.md` context and `tasks.md` completed phases to enrich the PR Summary, Changes, and Validation sections.

### Migration from v1

If you have an existing project using the `tickets/active/` layout:

1. Re-run `/dmx/init` — it will refresh the IDE rules to the `0.2.0` marker and update `activeContext.md` to the learning-inbox structure.
2. If you have an active ticket in `.dmx/tickets/active/{ref}/`, copy `spec.md` and `tasks.md` to `.dmx/spec.md` and `.dmx/tasks.md` on the relevant branch. Add the YAML frontmatter block to the top of `spec.md`.
3. The old `tickets/` directory can be deleted — no skill reads from it any more.

### Migration — add `production_branch`

Projects initialized before configurable branch roles may have `.dmx/config.md` without `production_branch`:

1. Re-run `/dmx/init` — adds `production_branch` when missing; **does not overwrite** an existing value.
2. Until then, hotfix/release/close-ticket skills auto-detect when the repo has only `master` or only `main`. If **both** exist, set `production_branch` in config or re-run init (init will ask which is production).
3. `/dmx/create-pr` on a hotfix branch auto-targets `production_branch` when `base` is omitted (detects `**Type:** hotfix` in spec or a `hotfix-` branch prefix).
